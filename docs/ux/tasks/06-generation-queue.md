# 06 · Очередь генерации по отмеченным билетам (P1)

## Принцип
Подготовка ответов запускается **только вручную** по пунктам, которые Тома отметила в списке (задача 03). Автоматического запуска нет. Нагрузка на сервер (2 CPU, 2 ГБ) и на модель ограничена, поэтому нужна очередь.

## Что сделать
- Вынести ядро генерации из `generate_ticket_answer` в функцию, не зависящую от HTTP-соединения: собрать контекст → вызвать модель → сохранить ответ. SSE-эндпоинт одиночной генерации (задача 04) использует её же.
- `POST /api/subjects/{slug}/tickets/generate` с телом `{ticket_ids: [...], depth, wishes, skip_done: true}`. Пункты с уже готовым ответом пропускаются, если `skip_done`; «Составить заново» для одного билета — явное действие без `skip_done`.
- Статусы `exam_tickets.status` расширить: `queued`, `generating`, `error` (+ `error_text`). Фоновый обработчик берёт билеты по одному (`MAX_PARALLEL_GENERATION`, по умолчанию 1; пауза `GENERATION_DELAY_SEC`, по умолчанию 0). Очередь **переживает закрытие страницы и перезапуск сервиса**.
- `GET …/tickets/queue` (или поля в списке билетов): `{total, done, failed, running_ticket_id}`.
- `POST …/tickets/queue/cancel` останавливает очередь предмета; `POST …/tickets/{tid}/retry` повторяет ошибочный.
- Одна активная очередь на пользователя; повторный запуск пополняет текущую.

## Интерфейс
- Панель «Подготовить ответы (N)» (см. задачу 03): глубина, пожелания, «Пропустить уже готовые», оценка «Это займёт около M минут».
- Во время работы: карточка «Готово 1 из 3 · можно закрыть страницу», кнопка «Остановить». Билеты: «в очереди» / «пишу…» / «готов» / «ошибка · Повторить».

## Критерии приёмки
- Очередь из 40 отмеченных проходит до конца при закрытой вкладке; прогресс виден при возврате.
- Перезапуск сервиса в середине очереди не теряет билеты.
- Ошибка одного билета не останавливает остальные.
- Память не растёт линейно с числом билетов.

## Ограничения среды
- Лимиты и бюджет модели владелец снял. Пробную очередь из 5 билетов всё равно сделать как проверку (время и ошибки), а не для согласования расхода.
- Сервер скромный (2 CPU, 2 ГБ; возможна смена тарифа, см. `STATUS.md`). `MAX_PARALLEL_GENERATION` по умолчанию 1. Очередь не должна ждать завершения описания картинок (`_IMAGE_SEM`) и индексации (`_INDEX_SEM`): это отдельные семафоры, но перед запуском проверить, что поиск (`embed_query`) не страдает при одновременной индексации.
- Генерация подставляет в контекст только текстовые чанки активных источников и кандидатов-картинок по правилам задач 04 и 11.
