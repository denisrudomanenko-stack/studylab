# StudyLab — UX-задания для реализации

Проектирование и дизайн ведёт Claude (дизайнер), реализует Claude Code. Здесь лежат задания и входные материалы.
Визуальная карта (персоны, CJM, экраны): [`ux-map.html`](ux-map.html) — открыть в браузере.

## Главный приоритет

Путь **«источники → идеальный ответ на билет»**. Тома загружает материалы предмета один раз сама, ведёт список из 30–50 билетов (вручную или из файла),
отмечает нужные пункты и **сама запускает** подготовку: конспект ответа только из её материалов, с источником у каждого тезиса.
Ничего не готовится автоматически.
Сегодня она делает то же в DeepSeek вручную, билет за билетом. StudyLab должен быть быстрее и надёжнее.
Всё остальное (прогресс, повторение, телефон) идёт после.

## Контекст

- Пользователь: Тома (студентка, роль `student`). Админ (Денис) на этапе тестирования только проверяет и поддерживает.
- Масштаб: 10+ предметов, 30–50 билетов в каждом, иногда больше. Даты экзаменов известны заранее. Предметы относятся к семестрам (сейчас у Томы 3-й семестр, 2 курс).
- Устройства: ноутбук и планшет — подготовка и работа с ответами. Телефон — **только** чтение готовых билетов и ассистент.
- Глубина ответа всегда разная: задаёт студентка (Кратко / Стандарт / Подробно + «Пожелания»).

## Что уже есть в коде (проверено по `studylab.py`, 3072 строки)

- Таблицы: `users`, `subjects` (нет даты экзамена), `sources`, `conversations`, `chat_history`, `password_reset_requests`, `exam_tickets` (`question`, `answer`, `status` pending/generated).
- Права: `POST /api/subjects`, `index`, `activate`, `deactivate`, `rename`, `DELETE source` требуют `admin_user`. `upload` доступен любому. В интерфейсе все эти кнопки показываются только админу (`isAdmin`).
- Загрузка не запускает индексацию: статус `uploaded`, дальше админ жмёт «Индексировать». Статусы: `uploaded → indexing:<фаза> → indexed → active/inactive`, `error`.
- Билеты: `POST …/tickets/batch` уже принимает список строк (одна строка = вопрос, снимает нумерацию). Генерация — `GET …/tickets/{tid}/generate` (SSE, один билет, одно соединение, сохраняет ответ в `finally`).
- Промпт ответа на билет требует «если в источниках нет — используй общие знания (пометка «Из общих знаний:»)». Это **противоречит** новому принципу «только из материалов».
- `_rag_context` ищет по активным источникам **всех** предметов. Для билетов это нежелательно (см. задачу 04).
- Провенанс в ответах: `[src:SLUG#SEG | раздел: заголовок]`. `md()` превращает его в ссылку `#/reader/<slug>?src=…&seg=…`, читалка открывает нужный сегмент (`?src&seg`). Экспорт: `_md_to_html` (регулярка около строки 1364).
- Дизайн «Ночной атлас» уже внедрён (токены в `:root`, две темы, классы `.chip`-подобных элементов нет — есть `.badge`, `.prov`).

## Правила реализации (обязательны для всех задач)

1. Один файл `studylab.py`; фронтенд — raw-строка `HTML_SPA = r"""…"""`. Новых зависимостей не добавлять без согласования.
2. Не ломать `TICKET_HTML_TEMPLATE` (использует `.format`, двойные скобки `{{ }}`) и `_md_to_html`.
3. Миграции БД — по существующему шаблону в `init_db` (`ALTER TABLE … ADD COLUMN` в `try/except sqlite3.OperationalError`).
4. Safari обязателен: `-webkit-backdrop-filter`, без `inset`, `dvh` с запасным `vh`, `:focus-visible` отдельным правилом.
5. Цвета только из токенов (`var(--accent)` и т.д.), обе темы. Цели нажатия ≥ 44 px.
6. Тексты интерфейса — из [`copy.md`](copy.md). Что отсутствует — спросить дизайнера, не выдумывать.
7. Проверка перед PR: `python3 -m py_compile studylab.py`; вынуть скрипт SPA и `node --check`; открыть страницу в headless Chromium и убедиться, что нет ошибок консоли.
8. Одна задача — один PR, ветка `feat/ux-NN-…`. В описании PR: что сделано, чего нет, как проверить.
9. После каждой задачи обновлять `CLAUDE.md`, если меняется архитектура или правила.
